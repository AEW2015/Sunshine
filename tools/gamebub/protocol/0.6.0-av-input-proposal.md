# Audio and ordered controller preparation — 0.6.0 proposal

Status: **receiver proposal under coordination; UDP headers are not agreed or
implemented**. Existing JPEG/MSV1 video and MSF1 feedback remain as documented in
0.5.0. This document does not authorize interpreting new bodies as MSV1 video,
or injecting unsequenced MSF1 button states. No stock Moonlight behavior changes.

## Audio proposal supplied by receiver agent

Proposed host-to-MoonBub destination: UDP5534. Codec payload: stereo four-bit
IMA ADPCM using the WAV block syntax,512 bytes per independently decodable block,
505 sample frames per channel. A raw block is not a complete RIFF/WAV file.
The first8 bytes contain little-endian signed16-bit predictor, step index0..88
and reserved zero per channel. Remaining data uses WAV IMA stereo grouping:
four bytes for left then four for right, low nibble first, repeated63 times.
Every block restores its own predictor/index; loss must not require a prior
audio block to decode the next one.

The proposed rate is48,293 sample frames/s, based on a receiver-reported DAC
rate of approximately48,292.729Hz. One block lasts approximately10.457ms, with
391,699 payload bits/s. Nominal IPv4/UDP adds about21,421 bits/s before any
application header, link framing or retries. These are arithmetic rates, not
measured Wi-Fi goodput. Even rounded nominal clock agreement does not eliminate
oscillator drift; buffer-fill telemetry and a bounded correction policy remain
necessary. ESP32-to-FPGA forwarding is proposed signed16-bit stereo PCM into a
bounded buffer; byte order, register/write contract and capacity remain pending.

The host implementation currently captures Windows output at the device's
48kHz rate, requests stereo from its shared WASAPI loopback endpoint, resamples
to48,293Hz and produces verified512-byte blocks locally. This does not establish
ESP32 decode, FPGA playback, drift stability or audio/video synchronization.
At offline EOF it discards and reports a short tail; the live design must keep
resampling across input reads rather than padding each capture callback.

Before live transmission, agree a header/version containing explicit codec and
configuration, established session identity, wrapping block sequence, first
sample index/timestamp, payload length and integrity coverage. Agree reset,
reordering/duplicate handling, missing-block concealment, late-drop threshold,
startup fill, buffer capacity, overflow/underflow reporting, disconnect/mute,
clock/PTS relationship and end-of-session behavior. No application-header layout
or CRC placement is selected by this proposal.

Audio must have an independent bounded queue and deadlines. It must not sit
behind a complete JPEG frame or cause video to catch up in bursts. Define whether
the existing2Mbps cap is video-only or aggregate; adding this audio to a2Mbps
video ceiling exceeds2Mbps combined. A shared scheduler/reserved budget needs
measurement with receiver queue and audio-buffer telemetry before a soak.

## Controller contract to agree

Use a separate receiver-to-host snapshot message, independent of video frame
IDs and MSF1 ACK ordering. Establish the peer/session before accepting input.
Agree session representation, input sequence width/wrap rule, twelve-button mask,
snapshot cadence/heartbeat, timestamp semantics, integrity and disconnect/reset
messages. Do not use an old session's packet as an automatic session restart.

The local `OrderedInput` adapter currently tests a nonzero16-byte session token,
unsigned32-bit input sequence and250ms silence timeout. These are local adapter
parameters for receiver review, not a frozen wire layout or an authentication
mechanism. Fresh full snapshots advance sequence even when buttons are unchanged;
duplicates/reordered/wrong-session messages cannot refresh liveness. Half-range
sequence ambiguity is rejected. Neutralize on silence, orderly close or driver
failure; detach the virtual controller when its session ends. The network loop
must tick expiry independently of incoming traffic and video progress.

Preserve the existing12-bit Game Bub mask and named digital Xbox mapping from
0.3.0: D-pad, A/B/X/Y, L/R bumpers, Start and Select/Back. Home, volume and power
remain handheld controls. Sticks and triggers are neutral; this does not provide
all controls needed for games such as Elden Ring. Additional analog mapping is a
separate decision, not an implicit reinterpretation of the D-pad.

The Windows adapter builds the repository-pinned ViGEm user-mode DLL and accepts
only an explicit absolute DLL path. It does not install drivers. The real probe
currently returns `VIGEM_ERROR_BUS_NOT_FOUND (0xe0000001)`; fake-driver tests
verify ABI, ordering, cleanup and release behavior. Physical Windows controller
recognition and Game Bub button-to-game behavior remain unverified.

## Qualification gates

1. Agree exact headers, session establishment and receiver implementations.
2. Compare deterministic audio block/PCM hashes with ESP32 decoding; test channel
   identity, silence, block loss/corruption and recovery before physical playback.
3. Verify the signed Windows controller driver/backend, then one button/release,
   chords, reordered/duplicate input, timeout, reconnect and unplug in a controller
   tester. Confirm neutral on every exit; do not inject MSF1 snapshots.
4. Test audio-only playback and record ring fill, under/overruns and drift for at
   least ten minutes. Measure DAC playback rather than treating UDP send as sound.
5. Add known-good5fps JPEG video with aggregate pacing; measure audio continuity,
   synchronization, input latency and receiver queues before increasing video FPS.
