# Game Bub fixed-mode protocol decision record — 0.2.0-draft

Status: **host proposal; receiver-agent agreement and wire format pending**.
This revision extends [0.1.0-draft](0.1.0-draft.md), which remains the record of
video geometry, codec questions, frame bounds, integrity, and receiver validation.
The scope below supersedes that revision's product-feature assumptions.

## Product scope

Provide one lightweight, explicitly identified Game Bub session with video,
audio, and simple button input. The initial video canvas is 720×480 at 30 fps,
with the 720×405 16:9 image centered at y=37. A later 60 fps target requires
measurements. The receiver agent must choose the video codec and exact decoder
restrictions before the one profile is finalized. The one profile will include
one audio codec and fixed audio parameters agreed with that agent.

There is no need for a general Moonlight feature set or user-facing codec
selection in this dedicated mode. Existing stock-client behavior must remain
intact. Use a distinct, explicit mode identity and verify an exact protocol and
profile match before a session; reject mismatches and never identify JPEG as
H.264. Pairing or equivalent authorization and session identification still
need agreement before accepting control input. Video-only remains a laboratory
diagnostic for initial receiver tests; normal operation includes audio.

## Audio decisions for the receiver agent

Agree the following before selecting an audio encoding or packet layout:

| Topic | Required decision |
| --- | --- |
| Output hardware | Speaker/DAC interface, native rate, channels, bit depth, and buffer constraints |
| Encoding | PCM or supported audio codec, exact profile and decoder restrictions |
| Block duration | Samples per block, maximum encoded bytes, decode and playback budgets |
| Timeline | Capture timestamp units, audio sample clock, audio/video common epoch and wrap |
| Scheduling | Audio and video bandwidth reservation, queue bounds, jitter and latency limits |
| Recovery | Gaps, loss, duplicate or reordered blocks, silence/concealment, reset and reconnection |
| Drift | Device clock measurement and bounded correction without accumulating latency |

Determine whether decoding occurs on the ESP32 or FPGA and how it competes with
Wi-Fi, QSPI, video decoding, display and button handling. Audio must not queue
indefinitely when video stalls. Dropped or expired blocks create an explicit
discontinuity; the agreed receiver must define how to resume. Protect complete
blocks with the agreed session, length and integrity rules. Timestamp and buffer
fields in the local test core are host-only and are not a packet format.

## Button decisions for the receiver agent

Agree the physical buttons, logical names, Windows keyboard/gamepad mapping,
debounce, state update cadence, sequence width/wrap, session identity, and
disconnect timeout. A complete button-state snapshot can recover from a lost
release when a later snapshot arrives; the receiver must repeat snapshots often
enough for the agreed latency. Ignore old or duplicate states within a session,
and release all injected buttons on disconnect, timeout, or input-adapter failure.
The host must gate input by the active authorized session; old packets must not
be accepted after reconnect. A sequence reset alone is not session identification.

## Local foundation and acceptance

`../realtime.py` provides a thread-safe latest-frame slot, a bounded audio FIFO,
drop/discontinuity accounting, and logical button snapshots. Its limits are
explicit constructor inputs because the receiver capacities are not known. It
does **not** capture sound, encode audio, transmit data, inject Windows input,
or implement the session handshake. Caller-provided timestamps use one host
monotonic clock; device timestamps need conversion before use. Stop and join old
producers and reject old-session messages before resetting these local objects.

The dedicated mode is complete only after the chosen profile is accepted by
both teams, real capture and input adapters are connected, and receiver tests
verify bounded video/audio latency, continuous audio recovery, button releases,
A/V synchronization, CPU load and gameplay at the target resolution and rate.
Measure audio-only, video-only diagnostic, and combined audio/video/input runs
to identify resource contention. Never report a buffer unit test as playback.
