Status: **not agreed with ESP32/FPGA agent; no wire format allocated**.
Host implementation: `gamebub/host`, based on Sunshine `3d6e1d60`.
This file is the host-side versioned copy to exchange with the receiver agent.
No receiver response, approved decoder reference, or hardware test result has
been received. Neither this document nor the fixture manifest is negotiation.

## Confirmed product requirements

- Windows host; Wi-Fi → ESP32-S3 → QSPI → FPGA.
- Initial canvas 720×480, full color, 30 fps. 60 fps requires later measurements.
- Square-pixel 16:9 input is scaled to 720×405, at x=0, y=37, with 37 top and
  38 bottom black rows. Other aspect ratios fit within that viewport without
  distortion. The display must not stretch the full canvas back to 16:9.
- Video-only operation must be possible for initial validation.
- JPEG must have its own explicitly negotiated codec identity. It must never
  be carried under H.264's GameStream identifier or advertised to stock clients.
- Preserve stock Moonlight behavior and Sunshine pairing, launch, and input
  where practical. Integration follows successful standalone receiver tests.

## Codec capability exchange — awaiting receiver

Obtain an accepted encoded sample and identify the **actual FPGA decoder**.
Agree which side sends capabilities, the selection/acceptance sequence,
timeouts, maximum control message size, and session authentication before
choosing a control transport. No allocation is implied by the logical names below.

| Capability | Required precision in the agreed specification |
| --- | --- |
| codec | Separate JPEG identity, or separately specified H.264 identity |
| canvas/viewport | Exact dimensions, square-pixel convention, bar rows, RGB order |
| color | YCbCr conversion matrix/range, component order, display RGB precision |
| rate | Accepted rate, timestamp timebase, pacing tolerance |
| JPEG | Baseline SOF0, sample precision, components, permitted sampling factors |
| Huffman | Fixed/programmable tables, DHT required/forbidden, reference table bytes |
| quantization | Allowed table IDs and precision; DQT requirements; quality bounds |
| restart | DRI required/forbidden, MCU interval limits, RST sequence rules |
| markers/scans | APP/COM acceptance, single interleaved scan, marker fill-byte handling |
| limits | Complete JPEG size including markers, decoded stride, MCU edge padding |
| H.264 alternative | Exact profile/level, CABAC/CAVLC, refs, slice types/count/size, B-frame rules, SPS/PPS and IDR handling |

For an H.264 selection, validate SPS/PPS **and slices** from encoded output:
profile/constraint bits/level, chroma/bit depth, `entropy_coding_mode_flag`,
reference counts and reference-list use, picture/slice structure, and absence
of prohibited B slices. Encoder options alone do not establish compatibility.
The current laboratory does not implement an H.264 sender or validator.

## Logical frame and packet fields — layout deliberately pending

The receiver agent must agree field widths, signedness, byte order, alignment,
version/magic placement, control/data separation, and transport before a layout
is implemented. JSONL logs and fixture manifests are local files, not packets.

| Logical field | Behavior to agree |
| --- | --- |
| session ID | Distinguishes restarts/reconnects from old datagrams and frame wrap |
| frame ID | Strictly increasing within a session; width and wrap/reset rules |
| timestamp | Capture time vs presentation time; monotonic epoch, units, width |
| codec/config ID | Binds every frame to the accepted codec/capabilities revision |
| dimensions | Negotiated canvas, viewport, permitted reconfiguration procedure |
| frame byte length | Validated against negotiated hard bound before allocation |
| chunk identity | Frame ID, byte offset or chunk index, payload length, final-chunk rules |
| chunk bound | MTU and ESP32/QSPI buffer constraints, including all header overhead |
| integrity | Chosen algorithm, polynomial/reflection/init/xor, byte coverage and order |
| feedback | Receive/consume/display frame IDs; available complete-frame credits |

Agree UDP versus TCP or an existing receiver transport; loss/reorder behavior
and head-of-line blocking implications differ. Avoid IP fragmentation if UDP
is selected; determine usable payload size from measured path MTU. Specify
duplicate, overlap, out-of-order, inconsistent-length, and truncated chunks.
Never allocate from unchecked length or accept chunks from a different session.
Complete-frame validation must precede handing a frame to a nonrecoverable decoder.

Local fixtures use Python/zlib CRC-32 (CRC-32/ISO-HDLC: reflected polynomial
0xEDB88320, standard init/xor, check value for ASCII `123456789` = 0xCBF43926)
over the entire JPEG, shown as eight hexadecimal digits. This is a local
integrity reference, **not a selected packet checksum**. SHA-256 covers exact
file bytes. Integrity checks do not authenticate a network peer.

## Bounds, backpressure, and recovery — acceptance decisions pending

The agreed maximum frame size must fit the smallest receiver-stage capacity;
document ESP32 RAM/PSRAM, DMA alignment, QSPI transfer bounds, FPGA compressed
buffer size, and display-buffer ownership. Define the largest legal chunk and
maximum concurrent incomplete frames. Receiver credit must reflect the slowest
downstream stage, rather than just Wi-Fi reception.

Proposed behavior for receiver review:

1. Start with one complete-frame credit and bounded reassembly memory. No frame
   enters the hardware decoder until length/integrity/codec restrictions pass.
2. Sender has at most one encoded frame in flight and no waiting-frame queue;
   capture the newest frame when ready. Reduce JPEG quality within bounds when
   rate/age exceeds budget. Drop stale or oversize frames; report all drops.
3. Define credit units, credit return on consumed vs displayed frames, sequence
   handling, feedback expiry, and cancellation acknowledgment. No new frame on
   zero or stale credits. Reclaim resources on agreed timeout/disconnect.
4. On loss, decide whole-frame discard vs bounded retry before the deadline.
   JPEG recovery should begin on a new complete frame, not partial corruption.
   Specify display-last-good vs blanking behavior, timeout, and decoder reset.
5. On CRC/length failure, discard and report reason; do not advance display ID.
   On QSPI stall or FPGA overflow, stop credits and reset only by agreed handshake.
6. Reconnect uses a new session and fresh capability agreement. Reject old frames.
   Unknown codec, version, or incompatible limits must not fall back to H.264.

The host laboratory has no receiver feedback. It models zero protocol overhead,
one serial transmission at a configurable bit rate, a configurable host age
deadline, no queue, and dropped pacing slots. This model cannot establish a
real link budget, backpressure correctness, or recovery interoperability.

## Receiver validation gate

First inspect and decode `../fixtures/` offline. Record accepted variants;
reject unsupported variants cleanly. SHA/CRC must match compressed bytes. Use
lossless PNG for geometry and reference colors; JPEG is lossy, and hardware
IDCT rounding may differ from the host RGB hash. Agree error tolerances instead
of requiring bit-exact host-decoded pixels. Check bars, channels, fine detail,
moving square, and binary frame-ID patch.

Then test the agreed framing with boundary-sized frames, all chunk boundaries,
loss/reordering/duplication, bad lengths/checksums, oversized frames, zero/stale
credits, disconnect/reconnect, frame/session wrap, QSPI stalls, and decoder
failures. Bound memory, stale-frame age, and time to first good frame after fault.

Only after this gate passes: implement an opt-in Sunshine codec extension with
both server configuration and paired-client capability acceptance; run stock
Moonlight compatibility tests and a sustained moving-game-footage hardware run.
