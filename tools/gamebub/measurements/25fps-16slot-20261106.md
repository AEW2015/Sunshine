## Interpretation and next controlled tests

Two limits coexist: pre-send replacements and longer host packet intervals
limit delivered rate; the receiver also saturated its temporary queue.
There is no supplied packet-specific queue-drop map, so the 13 queue drops
cannot individually explain all ten frame failures. An inactive assembler
does not identify whether SOF was missing or rejected. These records do not
establish a radio fault or a particular consumer/QSPI stall.

Recommended sequence, each requiring fresh receiver/recording readiness:

1. Restore the previously used 32-slot queue and repeat this exact 30-second
   source/settings/pacing control. Change only queue capacity; preserve reasons,
   queue-drop identities and consumer/commit/ready timing. Do not change firmware
   logic, bitrate and host pacing at the same time.
2. If receiver outcomes reconcile, compare the existing optional hybrid600
   waiter with `sleep`, holding the new receiver configuration, 25 fps, Q25 and
   4 Mbps fixed. This is an explicit pacing experiment, not an unchanged run.
3. Only if remaining host replacements/demand justify it, compare 6 Mbps as a
   separate cap change. Do not assume a configured 25 fps label proves delivery.

Use fresh IDs, with 3,000,752 or higher only after checking subsequent use.
Keep AV mode and Wi-Fi power policy fixed across comparisons; require frame,
ACK and receiver accounting plus STOP and recording coverage. No next hardware
run was started by this analysis, and no installed service or source behavior
was changed.
