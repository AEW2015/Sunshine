# Windows RS24 host-control replay — 2026-11-04

This checkpoint adds a bounded native host-control model for the pinned MoonBub
v24 agreement, separate from live JPEG/AV and the v20 encoder. It does not
instantiate CP23 reference banks, parse JA23, reset a live pipeline or open a
custom receiver socket.

## Implemented behavior

- HELLO → OFFER → COMMIT → GO → RUNNING, binding every reply to the host boot
  identity, profile and outstanding proposal. Data remains blocked until GO_ACK.
- Exact retransmission of one outstanding packet, with a configurable 0–8 retry
  budget. Repeated BUSY consumes that budget. Exhaustion enters SAFE_STOP while
  retaining the outstanding identity; a late GO_ACK cannot resume it.
- A caller-owned in-memory epoch ledger reserves above both local and advertised
  peer epochs, never wraps and retains abandoned reservations. This is not durable
  atomic storage or boot-nonce generation.
- Explicit modeled drain/owner snapshots at start, before COMMIT and before the
  modeled reset transition. Transport, source, private candidate, reference-reader,
  frame-slot, packet and media-control owners independently block those transitions.

Nine new native regressions cover phase progression, all eight single-message
loss positions, repeated BUSY, lost GO_ACK, invalid/stale identity, epoch exhaustion,
reboots and late owners. One test reads actual `PacketLedger`/`SenderFrames`
accounting: consumed PC18 does not release a frame; FINISHED still retains the
frame; explicit RELEASE, removal of the packet account, media-control completion
and an independent modeled drain signal are all required for a clear snapshot.
This test is not production pipeline wiring or physical drain verification.

## Frozen campaign replay

`--recovery-replay RESULTS.json` consumes the same hash-pinned artifact as
[the wire checkpoint](v24-reset-wire-20261104.md). It checks exact outgoing bytes,
host phases, retry exhaustion and the final data gate across ten loss/nominal
campaigns and three reboot handshakes: 124 controls, 51 delivered host replies,
13 retry calls, one SAFE_STOP and final modeled reboot epoch 3.

The published rows contain direction, bytes, kind and delivery status; they
contain no owner/drain snapshots. Replay therefore injects **explicitly modeled
clear owners**. It does not independently replay receiver states, media reset,
write/vblank ownership, real socket/DMA completion or durable recovery. Reports
carry separate false flags for those unverified scopes. New epoch media still
needs independent-key/full-HUD enforcement in a future compatible CP23 path.

Build using the existing Windows/MSYS2 instructions, then run:

```powershell
& C:\msys64\msys2_shell.cmd -defterm -here -no-start -ucrt64 -c './cmake-build-gamebub-v20/gamebub-v20-conformance.exe --recovery-replay tools/gamebub/artifacts/v24-recovery-results-4025d355.json'
& C:\msys64\msys2_shell.cmd -defterm -here -no-start -ucrt64 -c './cmake-build-gamebub/tests/test_sunshine.exe --gtest_filter="Gamebub*"'
```

The real-command Python regressions use `GAMEBUB_V20_EXE` and
`GAMEBUB_V24_RESULTS`, as documented in the wire checkpoint. Both new CLI tests
run without hardware, and missing/modified artifact provenance fails closed.

An existing JPEG demo cannot substitute for custom-codec qualification.
